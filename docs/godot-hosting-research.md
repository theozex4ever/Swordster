# Godot playtest hosting research

Verified 2026-11-08 against official documentation. Scope: Godot 4 single-thread Compatibility Web build plus standalone Windows ZIP; desktop Chrome/Firefox and Android Chrome; no Safari/iOS requirement. Anyone may access/forward the link; confidentiality is unnecessary. CI builds automatically, but publication requires an explicit action. No accounts, repository visibility, entitlements, or deployment permissions were assumed or changed; no hosted build was tested.

## Recommendation

Use **one itch.io HTML project**, with a browser build and Windows download, configured **Public + Unlisted in search & browse + No payments**. Remove it from the creator profile as well. This is the simplest documented fit for reduced discovery and anonymous access. Keep automatic CI artifact production separate from a manually triggered publish workflow. GitHub Pages plus public release assets is technically suitable hosting, but does not supply equivalent unlisted discovery semantics. Details and limitations follow.

## Web/mobile requirements and limits

- Use Compatibility/WebGL 2.0 with **Thread Support and Extensions Support disabled**; their enabled modes require cross-origin isolation. Export as `index.html`, keeping generated companion files together. Serve HTTPS and `.wasm` as `application/wasm`. Godot recommends Chromium/Firefox and warns mobile Web performance is lower than native. Audio/fullscreen need user interaction. These requirements make both static hosts plausible, not device-performance guarantees. [Godot Web export](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- itch: package all Web files with root `index.html`, relative paths, and case-correct UTF-8 names. Enable **Mobile Friendly** after validation. Mobile always uses click-to-launch fullscreen; without the flag it displays a warning but still allows launch. Limits: 1,000 files, 240-character paths, 500 MB extracted total, 200 MB per extracted file. These HTML limits remain relevant despite butler's larger upload allowance. [HTML5/mobile requirements](https://itch.io/docs/creators/html5)
- Pages project URLs normally include `/<repository>/`; verify relative asset paths there. MIME types come from GitHub's MIME database and cannot be customized per repository/file. Published site limit: 1 GB; soft bandwidth limit: 100 GB/month; deployment timeout: 10 minutes. The soft ten-builds/hour limit excludes custom Actions workflows. Releases allow files **under 2 GiB**, up to 1,000 assets/release, with no stated total-release-size or bandwidth quota. [URL layout](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), [MIME handling](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site#mime-types-on-github-pages), [Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), [Release quotas](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases#storage-and-bandwidth-quotas)

## Build, explicit publication, and rollback

**Common proposed workflow:** pin the Godot editor and matching export templates; CI calls the same local script to export Web and Windows, package both, and retain a pair identified by commit/build ID. Headless `--export-release` requires configured presets and existing output directories. Windows delivery must include the executable and its accompanying PCK/resources. [Godot CLI](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html#exporting), [Windows export](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)

Automatic build jobs should only store CI artifacts. A separate **workflow_dispatch** publish action should select a successful retained build pair, rather than silently rebuilding a moving branch. Manual dispatch requires write access and a workflow on the default branch. Actions artifacts require a GitHub login to download and normally expire after 90 days, so they are staging/rollback storage, not tester links. Retain approved rollback pairs deliberately. Standard hosted runners are free for public repositories; private-repository compute/storage allowances and overages depend on the owner's plan. [Manual dispatch](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow), [Artifact access/retention](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts), [CI billing](https://docs.github.com/en/actions/concepts/billing-and-usage)

### itch.io

1. Authorized creator creates the page, selects HTML/No payments, pushes initial builds, marks the Web channel playable, configures Mobile Friendly, selects unlisted, and explicitly saves Public visibility. Do this with unlisting configured before sharing. Page setup/publication is a dashboard step, not a documented `butler publish` command. [Page publication](https://itch.io/docs/creators/getting-started#publishing), [Butler HTML setup](https://itch.io/docs/butler/pushing.html#html-playable-in-browser-games)
2. Publisher authenticates with `butler login`; CI uses secret `BUTLER_API_KEY`. Official automation-friendly downloads are available via broth. [Authentication](https://itch.io/docs/butler/login.html), [CLI installation](https://itch.io/docs/butler/installing.html)
3. Illustrative commands inside the explicitly triggered publish job; paths/account/version are placeholders, not existing configuration:

   ```sh
   butler push artifacts/web.zip owner/swordster:html5 --userversion BUILD_ID
   butler push artifacts/windows.zip owner/swordster:windows --userversion BUILD_ID
   ```

   Existing-channel pushes update live downloads immediately; version labels do not control order. `--hidden` works only on **new** channels, not hidden updates to existing ones. Therefore automatic build CI must not push tester channels. [Push/version/hidden behavior](https://itch.io/docs/butler/pushing.html)
4. Proposed rollback: re-push a retained known-good pair; upload order determines current version. Versioned channels offer selection but add file management. The docs establish no atomic two-artifact switch. Butler's uncompressed build ceiling is 30 GB; HTML limits above are stricter. [Channel/version behavior and limits](https://itch.io/docs/butler/pushing.html)

### GitHub alternative

Configure Pages for GitHub Actions. Its official workflow uses `configure-pages`, `upload-pages-artifact`, and `deploy-pages`; deployment requires `pages: write`, `id-token: write`, and a Pages environment. Put deployment in the explicit publish workflow. [Custom Pages workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

Release upload/publication can be separated with the authenticated CLI (illustrative existing remote tag):

```sh
gh release create TAG artifacts/windows.zip artifacts/web.zip --repo OWNER/REPO --verify-tag --draft --notes "Playtest BUILD_ID"
gh release edit TAG --repo OWNER/REPO --draft=false
```

`--prerelease` labels maturity; it does not mean unlisted. Keep version-specific release URLs. Proposed rollback: redeploy retained old Web files and point the Windows link at the matching old release; optionally change which release is Latest. Pages deployment and release publication are separate operations. If immutable releases are enabled, published assets/tags cannot be replaced; publish a new version or reuse an old release. [CLI creation](https://cli.github.com/manual/gh_release_create), [CLI publication/latest](https://cli.github.com/manual/gh_release_edit), [Immutability](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

## Actual-host checks still required

- Confirm an authorized creator/repository owner, available slug, applicable plan, upload allowances, and CI publishing credentials; none are established here.
- In a signed-out clean browser, follow the final share URL, play, and download Windows without login/payment prompts; check itch profile removal and unlisted settings. Documentation supports the path but does not validate this account's configuration.
- Test desktop Chrome/Firefox and physical Android Chrome: initial/cached load, WASM MIME/errors, tap-to-start audio, touch controls, viewport/orientation, fullscreen, pause/resume, and frame rate. Enable desktop/mobile texture formats if using VRAM compression. Test iframe storage if persistence is required. [Godot browser caveats](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- Download/extract/run the complete Windows ZIP on another Windows machine; record actual unsigned-download/launch warnings. Godot signing requires separate tools/certificate configuration. [Windows distribution/signing](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)
- Publish a later pair, then roll back; verify both visible build IDs and cold/cached clients, and measure loading/compression on the chosen host. No device, anonymous-download, or rollback smoke test was performed in this research.
